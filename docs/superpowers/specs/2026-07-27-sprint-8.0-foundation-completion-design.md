# Sprint 8.0 — Foundation Completion Design Specification

**Status:** Frozen v1.0
**Date:** 2026-07-27

## 1. Overview

### Design Principle: Correctness Before Capability

Sprint 8.0 prioritizes correctness over capability. No new platform capabilities
(DNS, Packet Tunnel, Safari Web Extension) are introduced until the existing
update pipeline, Content Blocker runtime architecture, and premium
infrastructure satisfy their production-readiness requirements.

### Objective

Complete the remaining production foundation before adding new platform
capabilities. At completion, the project has:

- a production-ready update pipeline,
- all four Content Blockers on the same runtime architecture,
- StoreKit foundation,
- no known correctness bugs in the update subsystem.

### Scope

Three epics, nine commits:

- **Epic 1 — Update Pipeline Completion:** Commits 1–4.
- **Epic 2 — Complete Content Blockers:** Commits 5–7.
- **Epic 3 — Premium Foundation:** Commits 8–9.

### Out of Scope

- Premium DNS
- Packet Tunnel
- Safari Web Extension
- Rule conversion implementation
- New Safari UI

### Parallel Tracks

- **Track A — Implementation (Claude Code):** the nine commits below.
- **Track B — Architecture (no implementation):** ADR-0002 (Rule Conversion
  Strategy & Licensing), ADR-0003 (ADBLXShared Adoption), Sprint 8.1 DNS ADRs.
- **Track C — External:** purchase Apple Developer Program, wait for
  activation, enable Network Extension capability, configure App Store
  Connect products.

### Architectural Constraints

Every commit in this sprint must respect these invariants:

- **Single update pipeline.** `.install` and `.remove` share the same
  composition → compile → atomic write pipeline. No parallel removal
  pipeline may be introduced.
- **Single source of truth.** `installed_filters.json` remains authoritative
  for installed filter state.
- **Single runtime architecture.** All four Content Blockers use the same
  App Group → bundled fallback loading pattern.
- **No new persistent state unless justified.** Metadata is stored alongside
  existing update state (e.g. `update_throttle.json` via `FilterStore`), not
  in unrelated stores such as `UserDefaults`.

### Cross-Cutting Concerns

- Bootstrap/update work stays off the main actor.
- No update-path work exceeds 16 ms on the UI thread.
- All filesystem mutations are atomic.
- Zero orphan temporary files after any transaction.
- Every update path remains rollback-safe. Any mutation that changes
  installed rules must preserve the rollback guarantees established in
  earlier sprints — `.remove` is not a special case.

## 2. Epic 1 — Update Pipeline Completion

### Commit 1 — Bootstrap Gate Fix

**Problem:** `ADBLXApp.swift` currently calls
`ContentBlockerBootstrap.ensureInitialRulesInstalled(pipeline:)`
unconditionally on every launch, inside a detached `Task`, with no gate and
no relationship to update checking (`UpdateCoordinator.run()` has no
production caller yet).

**Design:**

- `ensureInitialRulesInstalled` is gated: skip entirely when
  `ManifestStore.load() != nil`. No additional bootstrap flag is introduced.
- Launch ordering becomes sequential within a single detached, off-main-actor
  `Task`:

  ```text
  await ensureInitialRulesInstalled(pipeline:)
        ↓
  await UpdateCoordinator.run()
  ```

**Acceptance Criteria**

- Bundled snapshot installs whenever no cached manifest exists (fresh install
  or any relaunch before the first successful update).
- After the first successful update commits a manifest, bootstrap never
  writes again.
- Bootstrap remains entirely off the main actor.
- Launch ordering is sequential: bootstrap completes, then update evaluation
  begins.
- Regression tests cover:
  - fresh install → bundled snapshot installed,
  - relaunch before first successful update → bundled snapshot reinstalls
    successfully,
  - relaunch after first successful update → bootstrap performs no writes,
  - first launch with network → bootstrap then update execute in order.
- **Migration test:** an existing development installation (compiled rules
  present, no cached manifest) performs one final bundled-snapshot install on
  first launch after upgrading to Sprint 8.0, then completes the first
  production update, writes the cached manifest, and thereafter follows
  normal bootstrap gating. This is acceptable because there are no
  production users.

### Commit 2 — Production Update Trigger

Introduces the first production caller of `UpdateCoordinator.run()`, at
launch, with throttling and an in-flight guard.

**Throttle persistence:** a dedicated metadata file, `update_throttle.json`,
written via `FilterStore.writeMetadata` — not folded into `CachedManifest`
(which answers "what manifest have I downloaded", a transport-cache
question, not a scheduling question) and not `UserDefaults` (harder to
inspect/migrate, not naturally grouped with the rest of update state, which
already lives in `FilterStore`'s metadata directory).

- Persists the timestamp of the **last successful update** only.
- Written only on `run()`'s success paths (`.upToDate`, `.updated`); never on
  `.rolledBack`, `.rollbackFailed`, or a thrown error.
- Throttle interval is injectable (constructor parameter on the caller that
  wraps `UpdateCoordinator.run()` — throttle policy is a scheduling concern
  that stays outside the transactional `UpdateCoordinator` actor itself).
- An optional short failure cooldown may be added independently of the
  success throttle.

**Concurrency:** `UpdateCoordinator` tracks an in-flight
`Task<UpdateRunResult, Error>?` internally. A second caller while one is
already running awaits the existing task rather than starting a new
transaction. (Actor isolation alone is insufficient here — without an
explicit in-flight guard, two concurrent callers would each fully execute
the transaction serially, mutating filesystem state twice.)

**Acceptance Criteria**

- Launch evaluates update eligibility.
- Success throttle persists correctly.
- Concurrent callers cannot execute multiple update transactions.
- Filesystem mutations occur only once.
- Rollback executes at most once.
- Tests verify concurrent `run()` requests collapse into one transaction
  (a genuine concurrent-`Task` test, not sequential awaits).

### Commit 3 — Group Recomposition & `.remove`

**The gap:** `UpdatePlanner.plan()` already emits `.remove(filterID:)`, but
`UpdateCoordinator.run()` only processes `.install` actions today — `.remove`
is silently dropped. `FilterPipeline` has no `remove` method. Recomposing a
group after removing one source requires the *raw bytes* of the group's
remaining sources — and nothing today persists them.
`installed_filters.json` stores only metadata (id, version, checksum, rule
count); `Compiled/<Group>.json` stores compiled output, which is not
reversible back into per-source inputs. `FilterStore.Directory.filters`
(the `Filters/` subpath) is declared but currently unused — nothing reads or
writes it.

**Design — new invariant:**

> `Filters/` becomes the canonical local cache of verified source payloads.
> Every compiled ruleset must be reproducible solely from `Filters/` and
> `installed_filters.json`, without network access.

**Data flow:**

```text
install()
    ↓
Persist verified raw payload → Filters/<filterID>.json
    ↓
installGroup()  [pure: FilterSource[] → compose → compile → write → reload]
```

```text
remove(filterID:, group:)
    ↓
Load remaining sources' raw payloads from Filters/
    ↓
installGroup()
```

- **`installGroup()` stays a pure composition pipeline.** It accepts
  `[FilterSource]` and knows nothing about where sources originated (network,
  disk, bundled snapshot, future custom lists). Persisting raw payloads is
  `install()`'s responsibility, invoked before entering the shared
  `installGroup()` path — not folded into `installGroup()` itself.
- **`remove(filterID:group:reloadStrategy:)`** takes `group` explicitly
  (mirroring `install(_:reloadStrategy:)`'s `GroupComposition.group` — the
  caller, `UpdateCoordinator`, already knows the group from the
  `.remove(filterID:)` action's originating `InstalledFilter` entry). It
  loads `installed_filters.json`, filters to `group`'s entries excluding
  `filterID`, reads each remaining entry's payload from `Filters/`,
  reconstructs `[FilterSource]`, and calls `installGroup()`.
- **`UpdateCoordinator.run()` must also be updated to dispatch `.remove`
  actions.** Today, `run()` builds its `installGroups` list via
  `plan.actions.compactMap { if case .install(...) = $0 { ... } }` —
  `.remove` actions are filtered out at this exact line and never reach
  `FilterPipeline` at all. Adding `FilterPipeline.remove(...)` is necessary
  but not sufficient: `run()`'s action-dispatch logic must be extended
  alongside it to collect `.remove(filterID:)` actions and call
  `pipeline.remove(filterID:group:reloadStrategy:)` for each, using the same
  `snapshotForRollback()`/`restore()` pair and the same affected-extension
  reload batching already used for installs. The existing single
  `snapshotForRollback()` call happens once, before the install/remove loop
  begins — this ordering must be preserved (not moved inside the loop) so
  the snapshot captures pre-transaction `Filters/` state before any removal
  in the batch executes.
- **Metadata merge** changes from pure upsert to remove-then-upsert:
  existing metadata → remove deleted IDs → upsert remaining IDs.
- **Last-source removal** requires no special case: `sources = []` →
  `JSONArrayCompositionService.compose([], group:)` already produces a valid
  `[]` → written atomically as-is. The empty-array path is not new code, it
  falls out of the existing implementation.
- **Rollback is redefined** to cover the entire update state, not an
  enumerated list of directories: `FilterStore.snapshotForRollback()`/
  `restore()` extend to include `Filters/` alongside `Compiled/` and
  `Metadata/`. The contract is "rollback restores every persistent artifact
  owned by the update subsystem" — not "rollback restores directories X, Y,
  Z" — so a future new directory extends the same guarantee without a
  contract rewrite.

**Acceptance Criteria**

- Group recomposes after source removal.
- Multi-source groups preserve remaining sources.
- Last-source removal produces valid empty rules (`[]`), written atomically.
- `installed_filters.json` is updated (deleted entry removed, remaining
  entries preserved — asserted by exact remaining-ID set, not merely "removed
  ID absent," per this repo's set-equality testing gotcha).
- Rollback supports removal operations, including restoring a deleted
  `Filters/<filterID>.json`.
- Regression tests cover:
  - multi-source removal,
  - last-source removal,
  - rollback-after-remove (including `Filters/` restoration),
  - **remove → reinstall the same filter reproduces identical compiled
    output** (rule-for-rule, byte-for-byte if practical) — confidence that
    recomposition from `Filters/` is deterministic.

### Commit 4 — Temporary File Cleanup

**The gap:** `FilterDownloadClient.download` writes each downloaded filter to
`FileManager.default.temporaryDirectory` directly, with a bare
`\(entry.id)-\(UUID().uuidString).tmp` filename — shared system temp
directory, no dedicated subdirectory, nothing ever deletes these files.

**Design:**

- **Dedicated workspace:**
  `<system temp>/com.ADBLX.ADBLX.Downloads/`. No other component writes into
  this directory.
- **Ownership:** `FilterDownloadClient` (or a small dedicated workspace
  abstraction) owns the workspace's lifecycle — `UpdateCoordinator`
  orchestrates the transaction but does not know where temp files live or
  manipulate `FileManager` directly.
- **Cleanup policy:** transaction-wide, not per-file. Downloaded artifacts
  may still be needed through verify, install, and rollback; deleting files
  immediately after use buys nothing and forecloses future diagnostic needs.
- **Cleanup timing:** after the transaction has completely settled (commit or
  rollback), in a `defer`/finally, not interleaved with install/rollback
  steps.
- **Self-healing:** every transaction empties the workspace regardless of its
  initial contents — a prior crash that skipped cleanup does not leave
  permanent orphans; the next successful transaction self-heals.

**Storage-class boundary** (documented explicitly so future contributors
don't blur it):

> The temporary download workspace is transactional scratch space. `Filters/`
> is the canonical verified-payload cache. `Compiled/` holds installed
> runtime artifacts. `Metadata/` holds update state. No data required for
> future recomposition or rollback may remain solely in the temporary
> workspace after a successful transaction.

**Acceptance Criteria**

- Dedicated temporary download directory.
- Success leaves the directory empty.
- Failure leaves the directory empty.
- **Self-healing:** a workspace containing stale files before `run()` is
  empty after `run()` completes, regardless of the run's outcome.
- Automated tests enumerate the temporary directory after both success and
  failure.

## 3. Epic 2 — Complete Content Blockers

**Scope, frozen:** a pure port of the existing `ADBLXAdsBlocker` runtime
pattern to Privacy, Annoyances, and Regional. No protocol extraction, no
helper package, no shared abstraction, no generic loader. ADR-0003
(Track B) already acknowledges this duplication is temporary; this sprint
does not fight that decision.

**Reference implementation** (`ADBLXAdsBlocker/ContentBlockerRequestHandler.swift`,
already in the codebase):

- Reads `Compiled/Ads.json` from the App Group container.
- Falls back to bundled `blockerList.json` if the App Group file is absent.
- Logs via `Logger(subsystem: "com.ADBLX.ADBLX", category: "AppGroup")`
  (hardcoded subsystem — `Bundle.main` inside an extension resolves to the
  extension's own bundle ID, not the app's).
- `AppGroup.swift` (identifier constant `group.com.ADBLX.shared`) is already
  duplicated once, into `ADBLXAdsBlocker`'s target.

### Commits 5, 6, 7 — Privacy, Annoyances, Regional (one commit each, identical shape)

For each extension:

- Replace the stub `ContentBlockerRequestHandler.swift` (currently
  bundled-only, no logger, no App Group path) with the Ads pattern, reading
  `Compiled/<Group>.json` (`Privacy.json`, `Annoyances.json`,
  `Regional.json` — matching `RulePartitioner`'s existing
  `"\(group.rawValue.capitalized).json"` naming).
- Add `AppGroup.swift` (identical content to the existing two copies) to the
  extension's target.
- Add a synthetic bundled `blockerList.json` fallback (see below).

**Synthetic bundled snapshots**

- **Size:** 5–15 rules per extension — small enough to be an obvious
  fixture, large enough to exercise the loading path. Not intended to block
  real websites; not a "mini filter list."
- **Content, representative of each category:**
  - Ads: image resource, script resource, generic ad URL blocking rules.
  - Privacy: analytics endpoint, beacon, tracking pixel rules.
  - Annoyances: cookie banner assets, newsletter modal script, notification
    prompt script rules.
  - Regional: a few domain-specific regional ad examples.
- **Determinism:** bundled snapshots are static test fixtures committed to
  source control. They are never generated from live filter lists during the
  build.
- **Distinguishability:** each fixture should be visually distinguishable
  when inspecting logs or debugging — different rule counts and domains per
  category are expected and useful, so it's obvious during simulator testing
  which extension is serving its bundled fallback.

**Acceptance Criteria** (per extension — behaviorally identical to Ads, not
merely similar)

- Reads from `Compiled/<Group>.json` in the App Group when present.
- Falls back to bundled `blockerList.json` when compiled rules are
  unavailable.
- Emits the same structured logging pattern as the Ads implementation.
- Successfully loads a non-empty bundled snapshot.
- Behavior matches Ads except for the group filename.

**CI check:** a new step in `.github/workflows/ci.yml` (after "Generate
Xcode project") verifies all five `AppGroup.swift` copies (main app +
four extensions) are byte-identical. This check intentionally verifies file
identity, not semantic equivalence — it should not later be replaced by a
formatter or AST comparison.

## 4. Epic 3 — Premium Foundation

### Commit 8 — StoreKit Infrastructure

**Existing state:** `SubscriptionService` protocol
(`fetchStatus() async -> SubscriptionStatus`,
`purchase(_ planID:) async throws -> Bool`) already exists, with
`MockSubscriptionService` wired into
`AppCompositionRoot.makeUIDependencies`.

**Design:**

- New, narrower **entitlement service protocol**, distinct from
  `SubscriptionService`, so background update planning doesn't depend on
  UI-shaped types:

  ```swift
  protocol EntitlementService: Sendable {
      func isPremiumEntitled() async -> Bool
  }
  ```

- `StoreKitSubscriptionService: SubscriptionService, EntitlementService` —
  one concrete type backed by StoreKit 2 (`Product.products(for:)`,
  `Transaction.currentEntitlements`, a `Transaction.updates` listener for
  out-of-band entitlement changes).
- `.storekit` local configuration defines exactly two products: an annual
  auto-renewable subscription and a lifetime non-consumable.
- `AppCompositionRoot` replaces `MockSubscriptionService` with
  `StoreKitSubscriptionService` in the real dependency path.
  `MockSubscriptionService` is updated to expose only Annual and Lifetime
  (see pricing decision below) and remains available for previews/tests.

**Pricing tiers, frozen:** two paid tiers — **Annual** and **Lifetime**.
The existing mock's Monthly tier is removed; it was development scaffolding,
not a product commitment. This aligns Sprint 8.0 with the PRD's monetization
direction (Free / Premium Annual / Premium Lifetime) and reduces App Store
Connect setup, purchase paths, and edge cases to test. Adding Monthly later
is an additive product decision, not a Sprint 8.0 concern.

**Acceptance Criteria**

- Fully testable using Xcode's local StoreKit configuration.
- No App Store Connect dependency for local testing.
- Entitlement lookup is exposed through an injected async protocol suitable
  for background update execution.

### Commit 9 — Premium Paywall

**Design:**

- UI: subscription screen presenting Annual + Lifetime, purchase flow,
  restore purchases (`AppStore.sync()` / re-checking
  `Transaction.currentEntitlements`).
- `UpdatePlanner.plan(manifest:installed:)` gains an entitlement input,
  becoming `plan(manifest:installed:isPremiumEntitled:)`. Today,
  `.skipPremium` fires unconditionally for any never-installed premium
  entry with no entitlement awareness at all; after this change,
  `.skipPremium` fires only when `!isPremiumEntitled` — an entitled,
  never-installed premium entry is bucketed into `.install` like any other
  new entry. This is a signature change touching every call site
  (`UpdateCoordinator`, all existing `UpdatePlannerTests.swift` cases) and
  must land as one task, not split across a broken-build boundary.
- `UpdateCoordinator.run()` calls the injected `EntitlementService
  .isPremiumEntitled()` once per transaction, before planning.
- **Re-planning is lazy**, not automatic: purchase completion updates
  entitlement state immediately (UI reflects it right away — the toggle
  becomes enabled immediately), but does **not** trigger an automatic
  `UpdateCoordinator.run()`. Previously-skipped premium filters install on
  the next normal, launch-time, throttled update. Update triggers for
  Sprint 8.0 remain exactly: launch, and the existing throttle — introducing
  "purchase triggers an immediate update" is a new network-trigger policy
  decision explicitly deferred, not part of this sprint. (A future
  enhancement could add an explicit, user-initiated "Refresh Now" that
  bypasses the throttle — out of scope here.)

**Acceptance Criteria**

- Premium entitlement integrates with `UpdatePlanner`.
- Premium manifest entries are skipped while not entitled.
- Entitlement change does not trigger automatic re-planning; it takes effect
  on the next normal update cycle.
- Previously-skipped premium filters install during the next update after
  purchase.

end-to-end testing of manifest download, ETag/304 behavior, payload

## 6. Performance Requirements

### Main Thread

- Bootstrap metadata read remains off the main actor.
- No update work exceeds the 16 ms UI budget.

### Memory

- Maintain the existing Sprint 7 memory budget.

### Disk

- Atomic writes.
- Dedicated temporary directory.
- Zero orphan files after every transaction.

### Network

- Launch-time update evaluation only.
- Success-based foreground throttle.
- No unnecessary wakeups.

### Performance & Energy Verification

- **Main-thread budget:** verify with Instruments → Time Profiler; no
  update-path work exceeds 16 ms on the main actor.
- **Rule recomposition:** verify no measurable install/remove latency
  regression compared to Sprint 7.
- **Memory:** monitor recomposition and rollback paths with Instruments →
  Allocations; no unbounded growth from introducing `Filters/`.
- **Disk I/O:** raw payload persistence results in one write per filter
  install, no redundant rewrites.
- **Energy:** cleanup and throttling introduce no additional background
  wakeups; verify with Instruments → Energy Log across repeated
  launch/update cycles.

## 8. Risks

- **`Filters/` becoming live is the highest-risk change in this sprint.** It
  touches rollback (`snapshotForRollback`/`restore`), which is exercised by
  existing passing tests; regressions here are silent until a rollback
  actually happens in production.
- **`UpdatePlanner` signature change touches every call site** —
  `UpdateCoordinator` and all existing `UpdatePlannerTests.swift` cases.
  Mechanical but wide; must land as a single task (see gotchas.md's note on
  task boundaries that end in an expected broken build — this change should
  not be split that way).
- **StoreKit local testing does not validate real App Store Connect product
  configuration** (a Track C dependency). Commit 8/9 acceptance criteria are
  locally verifiable; the production entitlement flow needs manual
  verification once ASC products exist.
- **Increased persistent storage.** Introducing `Filters/` duplicates data
  already represented in `Compiled/`. This is intentional: compiled output
  is not reversible back into per-source inputs, offline recomposition
  requires verified source payloads, and deterministic rollback requires
  local source availability. Storage optimization is explicitly out of
  scope for this sprint.

## 9. Non-Goals

This sprint intentionally does not optimize rule compilation, composition
algorithms, or storage formats. Those concerns belong to the later
rule-conversion work (ADR-0002, Track B). Do not "improve" the new
`Filters/` cache while implementing it.

## 10. Sprint-Wide Acceptance Criteria

- After Sprint 8.0, every installed ruleset must be reproducible entirely
  from local persistent state (`Filters/` + `installed_filters.json`)
  without requiring any network access.
- Bundled snapshot installs whenever no cached manifest exists; bootstrap
  never writes again after the first successful update.
- Concurrent update callers collapse into one transaction; filesystem
  mutations occur once; rollback executes at most once.
- `.install` and `.remove` share one pipeline; rollback restores the entire
  update state (`Compiled/`, `Metadata/`, `Filters/`).
- Every transaction leaves the temporary download workspace empty,
  regardless of its initial contents.
- All four Content Blockers are behaviorally identical to the Ads reference
  implementation, differing only in group filename.
- Premium entitlement gates `UpdatePlanner` output; previously-skipped
  premium filters install on the next normal update after purchase.

## Freeze Status

**Status:** ✅ **FROZEN**

This specification resolves the bootstrap regression, defines update
throttling and concurrency behavior, establishes `Filters/` as the canonical
local source-payload cache required for `.remove` to work at all, ports the
Ads Content Blocker pattern to the remaining three extensions with explicit
fixture and CI requirements, and lays StoreKit foundation with entitlement
gating wired into the update planner via lazy re-planning. It is ready to
hand off to the writing-plans skill for task-level breakdown.
