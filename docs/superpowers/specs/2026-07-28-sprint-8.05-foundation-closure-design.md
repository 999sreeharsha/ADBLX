# Sprint 8.05 — Foundation Closure — Design

## Sprint Goal

Close all remaining infrastructure, operational, and manual verification items
from Phase 1 so the foundation can be formally declared complete before
beginning Release 1.0 development.

**Duration:** 0.5–1 day

**Scope Rule:** No new production features. No architectural refactoring.

## Non-Goals

Sprint 8.05 does **not**:

- introduce new user-facing functionality;
- change the update pipeline architecture;
- add CI/CD automation beyond the local deployment script;
- migrate hosting away from GitHub Pages;
- implement premium entitlement revocation (only promotes it to a Sprint 8.1
  release blocker);
- change StoreKit product identifiers or pricing;
- automate Safari manual verification.

## Task 1 — Manifest Hosting Decision

### Background

Sprint 8.0 intentionally left the production `manifest.json` hosting location
undecided. `AppManifestEndpointProvider.manifestURL`
(`ADBLX/AppCompositionRoot.swift`) currently points at a placeholder
(`https://example.invalid/manifest.json`), and the Publisher CLI's `publish`
command (`backend/tools/Publisher`) already generates
`backend/public/manifest.json` plus `backend/public/filters/<group>/*.txt`
locally given a `--publish-base-url` flag — it does not itself deploy
anywhere.

`backend/public/` is tracked in the same ADBLX repo (confirmed via `git
ls-files`) — it is not a submodule or separate repository.

### Decision

Host via **GitHub Pages, served from a `gh-pages` branch of this same ADBLX
repository** (not a new dedicated repo — `backend/public/` already lives
here).

### Production URLs

- Manifest: `https://harshaunofficial.github.io/ADBLX/manifest.json`
- Filters: `https://harshaunofficial.github.io/ADBLX/filters/<group>/<id>.txt`
- `--publish-base-url=https://harshaunofficial.github.io/ADBLX`

### Contract

`ManifestEndpointProvider` (`ADBLX/AppCompositionRoot.swift`) remains the sole
place this URL is expressed in application code. No other file — code,
script, or doc — should hardcode the GitHub Pages URL as an architectural
dependency; it is a deployment decision. If hosting later moves to a custom
domain or CDN, only `AppManifestEndpointProvider.manifestURL` changes.

`AppManifestEndpointProvider.manifestURL` is updated from the
`example.invalid` placeholder to the real Pages URL above; the existing
"Sprint 5 blocker" TODO comment is removed since the endpoint is now real.

### Deployment mechanism

A new script, `backend/tools/publish-pages.sh`, run manually from the repo
root after:

```bash
swift run publisher publish --publish-base-url https://harshaunofficial.github.io/ADBLX
./backend/tools/publish-pages.sh
```

The script is intentionally "dumb" — it has no knowledge of filter groups,
manifest structure, or versions. It only publishes whatever currently exists
under `backend/public/`, with no transformation or renaming, preserving
`Publisher` (produces the artifact) / `publish-pages.sh` (deploys the
artifact) as a clean separation of responsibilities.

Mechanics:

1. Maintains a persistent `git worktree` at `.gh-pages-worktree/`, checked
   out to the `gh-pages` branch, so the script never disturbs the active
   working tree/branch.
2. **Self-bootstrapping:** if `origin/gh-pages` does not exist yet, the
   script creates it as an orphan branch (no shared history with
   `main`/`dev`), pushes it, and creates the worktree. On every subsequent
   run, it reuses the existing branch and worktree.
3. **Idempotent:** copies `backend/public/*` into the worktree, commits only
   if the copy produced a content change, and pushes. If nothing changed, it
   prints `No changes to publish.` and exits `0` without creating an empty
   commit.

The worktree is a persistent, intentional part of the repository's local
development environment, not a hidden implementation detail — it is
documented (see below) so any contributor understands why `.gh-pages-worktree/`
exists.

### Documentation

Written into `docs/Architecture/Publisher.md` (currently a one-line stub).
Covers: the GitHub Pages hosting decision and rationale, the
`--publish-base-url` value, the `publish-pages.sh` bootstrap/idempotency
behavior, and why `.gh-pages-worktree/` exists and should not be deleted.

### Division of responsibility

**Delivered by this sprint (repository artifacts):**

- `backend/tools/publish-pages.sh`
- Self-bootstrapping, idempotent worktree logic
- `docs/Architecture/Publisher.md` documentation
- `ManifestEndpointProvider` code change
- Tested locally where possible

**Performed by the repository owner (operational, outside sprint automation):**

- Running `publish-pages.sh` for the first live push
- Enabling GitHub Pages in repository settings (serve from `gh-pages` branch)
- Verifying `https://harshaunofficial.github.io/ADBLX/manifest.json` and
  `.../filters/...` are publicly reachable

### Acceptance Criteria

- Live `manifest.json` accessible over HTTPS (verified by repo owner).
- Publisher successfully generates a deployable output (unchanged behavior).
- `ManifestEndpointProvider` points to the production endpoint.
- Existing tests continue to pass — no existing test references
  `ManifestEndpointProvider`/`AppManifestEndpointProvider` directly, so this
  is a drop-in value change.

## Task 2 — External Track (App Store Infrastructure)

### Objective

Prepare App Store infrastructure and capture it as a durable, repeatable
artifact — not institutional memory — even though the underlying actions
(Apple Developer membership, App Store Connect configuration, Sandbox
testing) are manual and performed by the repository owner.

### Deliverable

New document: `docs/AppStoreSetup.md`, structured as:

1. Overview
2. Product Configuration (Product IDs, Types, Pricing)
3. App Store Connect Setup (App, Subscription Group, Products)
4. Sandbox Verification (Purchase, Restore, Entitlement)
5. Operational Status Log

### Single Source of Truth

The document states explicitly at the top: **the product identifiers in
`Config/Configuration.storekit` are canonical — App Store Connect must mirror
them exactly.** The document does not become an independent source of truth
for pricing/IDs; it always defers to the `.storekit` config.

Current canonical values (read from `Config/Configuration.storekit`):

- `com.ADBLX.ADBLX.premium.annual` — Auto-Renewable Subscription — $19.99/year
- `com.ADBLX.ADBLX.premium.lifetime` — Non-Consumable — $49.99 one-time

### Sandbox Verification checklist

Ties external verification back to Sprint 8.0's shipped code:

- Annual subscription purchase succeeds.
- Lifetime purchase succeeds.
- Restore Purchases restores both correctly.
- `EntitlementService.isPremiumEntitled()` returns the expected result after
  purchase and after app relaunch.

### Operational Status Log

Columns: `Date | Environment | Action | Performed By | Result | Notes`, where
Environment is one of: Apple Developer, App Store Connect, Sandbox,
TestFlight. This distinguishes what was verified in Sandbox vs. TestFlight
months later.

### Acceptance Criteria

- Sandbox purchase succeeds (recorded by repo owner in the status log).
- Restore Purchases succeeds using a Sandbox account (recorded).
- Products visible in App Store Connect (recorded).
- No production code changes — product IDs already exist and already match
  between `Configuration.storekit` and application source.

## Task 3 — Manual Verification (Privacy, Annoyances, Regional)

### Objective

Repeat the runtime verification already completed for Ads
(`docs/Architecture/ManualVerification.md`) for the three remaining Content
Blocker extensions, which are structurally identical to Ads: same App Group
(`group.com.ADBLX.shared`), same bundled `blockerList.json` fallback, same
`com.ADBLX.ADBLX` logging subsystem — differing only in bundle ID and App
Group rule filename:

| Extension | Bundle ID | App Group rule path |
|---|---|---|
| Privacy | `com.ADBLX.ADBLX.PrivacyBlocker` | `Rules/Privacy.json` |
| Annoyances | `com.ADBLX.ADBLX.AnnoyancesBlocker` | `Rules/Annoyances.json` |
| Regional | `com.ADBLX.ADBLX.RegionalBlocker` | `Rules/Regional.json` |

### Checklist structure

Each extension gets its own section in `docs/Architecture/ManualVerification.md`,
mirroring the existing Ads section, split into:

**Automatable** (can be scripted via `xcrun simctl` or similar):

- Install the app
- Remove the App Group rule file
- Relaunch the app
- Collect logs

**Manual** (requires a human using Simulator/device + Safari UI):

- Enable the Content Blocker in Safari → Settings → Extensions
- Reload Safari
- Visit the test page
- Confirm blocking/fallback behavior

This split records which steps could migrate from Manual to Automated later,
without investing in that automation now — Sprint 8.05 does not build new
`simctl`/UI-automation tooling.

### Workflow

1. This sprint writes the three checklist sections (adapted from Ads,
   correct bundle ID/rule path substituted per extension).
2. Repository owner executes each checklist on simulator/device.
3. Owner reports results (or logs) back.
4. This sprint's Commit 3 records outcomes into each section's "Last
   verified" table, following the existing Ads table's format.

### Acceptance Criteria

All four blocker extensions (Ads + the three added here) have verified
runtime behavior recorded in `docs/Architecture/ManualVerification.md`.

## Task 4 — Premium Revocation Policy (Product Ledger)

### Current state

`docs/gotchas.md` already documents (final entry, dated 2026-07-28) that
`UpdatePlanner`'s entitlement gating only blocks new premium installs and
never revokes an already-installed premium filter after entitlement lapses —
explicitly scoped as deferred for Sprint 8.0.

### Change

Update that entry's status from "deferred" to **"required before Sprint 8.1
Release Candidate,"** with rationale: premium filter lists remaining
installed after entitlement expiry is acceptable for the Safari-only MVP, but
this policy must be implemented before the DNS Packet Tunnel ships, because
premium access would otherwise continue indefinitely after subscription
expiry once a second enforcement surface (DNS) exists.

The Sprint 8.05 completion report (Commit 5) records this decision and its
history — deferred in Sprint 8.0, promoted to a release blocker in Sprint
8.05 — preserving *when* and *why* the status changed.

No new documentation files (`ProductDecisionLog.md`, `Roadmap.md`, etc.) are
created — per YAGNI, a dedicated decision log/roadmap is only justified once
there are multiple recurring entries to collect. `docs/gotchas.md` and the
sprint completion report are sufficient homes for this single decision today.

### Acceptance Criteria

- `docs/gotchas.md` entry updated in place.
- Decision recorded in the Sprint 8.05 completion report.
- No new documentation structures introduced.

## Sprint Exit Criteria

Phase 1 (Foundation) is considered complete when:

- Manifest hosting path is implemented and documented.
- Deployment script exists and is self-bootstrapping.
- Manifest endpoint points to the production Pages URL.
- App Store setup documentation exists.
- Apple operational steps have documented verification checklists.
- Manual verification exists for all four Content Blockers.
- Premium revocation policy is promoted to a Sprint 8.1 blocker.
- Sprint 8.05 completion report is published.

**Completion of Sprint 8.05 marks the formal end of the Foundation Phase. All
subsequent implementation work belongs to the Release 1.0 phase of the
project.**
