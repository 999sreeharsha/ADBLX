# Sprint 4 — UI Implementation from Frozen Stitch Design

**Date:** 2026-07-21
**Status:** Approved
**Depends on:** Sprint 1 (rule pipeline), Sprint 2 (update pipeline), Sprint 3A (group composition) — all backend, no UI consumer yet.

## 1. Context

Sprints 0–3A built ADBLX's entire backend: filter validation, compilation, group composition, the update pipeline, and reload coordination — all covered by unit/integration tests, none of it has a UI. `ContentView.swift` is still the unmodified Xcode template.

Stitch MCP was connected today. A Stitch project already exists — **"ADBLX: Peaceful Ad Blocker"** (`projects/16038318836427840964`) — containing a named design theme ("Serene Shield") and screens for every destination in the product: Home Dashboard, Safari Protection, Advanced Filter Lists, DNS Protection, Premium Upgrade, Settings, About, Onboarding, and an Update Progress Sheet, several with light-mode variants.

This changes the shape of Sprint 4. It is not a "design from scratch" sprint — the visual design already exists and is authoritative. Sprint 4 is an **implementation sprint**: adopt the existing Stitch design system into SwiftUI, freeze the information architecture, and implement each screen behind a protocol-based service layer so real backend wiring can land later without touching views.

## 2. Design Authority

**Stitch is the canonical source for visual design.** SwiftUI implementation must faithfully reproduce the approved screens and theme. If implementation reveals a necessary visual adjustment (accessibility, Dynamic Type, platform behavior, or a technical constraint SwiftUI can't satisfy as designed), the change is reflected back in Stitch first, so the two never drift out of sync.

**Explicitly excluded from this IA** (do not add during implementation without a product decision): statistics/analytics dashboard, blocked-request history/logs, per-site controls beyond the existing allowlist, custom rule editor, diagnostics dashboard.

## 4. Design System

Extracted from the Stitch project's theme, not invented. Confirmed tokens:

- **Color:** Primary "Privacy Purple" `#5856D6` (`#3f3bbd` on-primary variant), Secondary "Safety Blue" `#0058BC`/`#0070EB`, full surface/on-surface/outline scale, semantic error/tertiary colors, light and dark variants defined per-screen in Stitch.
- **Typography:** Plus Jakarta Sans for headlines (large titles use negative letter-spacing), Inter for body copy, Geist for stats/labels/mono data (e.g. "148,291 rules blocked").
- **Spacing:** 8px base grid, 20px container padding, 16px stack gap, 32px section gap.
- **Shape:** `rounded-xl` (24px) for cards/modals, `rounded-lg` (16px) for buttons/inputs, full pill radius for toggles.
- **Elevation:** Tonal layering + soft ambient shadows (no heavy drop shadows); glassmorphic blur on nav bars/toolbars.
- **Brand keywords every screen must satisfy:** Calm, Transparent, Premium (from the theme's "Digital Sanctuary" brief — quiet, authoritative, invisible-until-needed).

This becomes a `DesignSystem` module in SwiftUI (`Colors.swift`, `Typography.swift`, `Spacing.swift`, `CornerRadius.swift`, `Shadows.swift`, `Animations.swift`), generated by reading the Stitch theme values directly — not re-derived or reinterpreted.

## 5. Presentation Architecture

Every screen follows the same layered pattern already established for the backend (`FilterPipeline`, `UpdateCoordinator` — constructed with injected, protocol'd dependencies via `AppCompositionRoot`):

```
SwiftUI View
     │
     ▼
ViewModel
     │
     ▼
Feature Service (protocol)
     │
     ├── Mock implementation   — Sprint 4 (this sprint)
     └── Real implementation   — later sprint, swapped behind the same protocol
```

Services are defined per user-facing feature area (`HomeService`, `ProtectionService`, `SubscriptionService`, `SettingsService`), not around internal backend types — `FilterPipeline` and `UpdateCoordinator` are never protocolized or exposed directly to the UI layer. A later sprint wires real implementations into `AppCompositionRoot` alongside the existing `makeFilterPipeline()`-style factories; views and ViewModels do not change when that happens.

## 6. Definition of Done (per screen)

A screen commit is complete when:
- **View:** SwiftUI layout matches the Stitch screen; verified in simulator for Dynamic Type, Dark Mode, and VoiceOver labels; navigation into/out of the screen works within the frozen IA.
- **ViewModel:** exists, unit-tested, contains no SwiftUI-specific logic, depends only on the feature's service protocol.
- **Service:** protocol defined around what the screen actually needs; mock implementation returns representative data.
- **Backend:** may remain mocked; real wiring is out of scope for this sprint.

## 7. Commit Sequence

One commit per item, matching the granularity used in Sprints 1–3A (small, single-responsibility, independently reviewable/revertible):

```
Commit 1   Adopt Stitch Design System (DesignSystem module: colors, typography,
           spacing, corner radius, shadows, animations — read from the Stitch theme)
Commit 2   Application Shell (TabView/NavigationStack per frozen IA, routing to
           placeholder screens, AppCompositionRoot extended with a mock
           dependency graph so subsequent screens request dependencies from it)
Commit 3+  Shared Component Library — grown organically: a component is built in
           the first commit that needs it (e.g. PrimaryButton, Card, StatusCard,
           SettingsRow, PremiumBadge, ProgressRing, ComingSoonState), not
           speculatively up front
Commit N   Home                       (View + ViewModel + HomeService + mock)
Commit N+1 Safari Protection          (incl. Categories)
Commit N+2 Advanced Filter Lists
Commit N+3 DNS Protection             (Coming Soon shell only — IA + copy, no backend)
Commit N+4 Premium                    (View + ViewModel + SubscriptionService + mock)
Commit N+5 Settings
Commit N+6 About
Commit N+7 Update Progress Infrastructure (UpdateProgressModel + shared sheet,
           presentable from Home and Protection)
Commit N+8 Onboarding
```

Exact component commits interleave with screen commits as new shared components are first needed — the sequence above fixes ordering of screens and infrastructure, not a rigid count.

Each commit must build successfully, pass all existing tests, introduce no Swift compiler warnings, and leave the application in a runnable state.

## 8. Testing

- ViewModels: unit-tested against mock services (state transitions, loading/error/success), following the existing XCTest conventions used for `FilterPipeline`/`UpdateCoordinator` tests.
- Views: manual simulator validation per the Definition of Done (§6) — Dynamic Type, Dark Mode, VoiceOver, navigation — since SwiftUI view logic isn't meaningfully unit-testable here.
- No snapshot/UI testing infrastructure is introduced this sprint (out of scope; revisit if visual regressions become a problem post-freeze).

## 9. Out of Scope for This Sprint

- Real backend wiring for any service (`FilterPipeline`, `UpdateCoordinator`, StoreKit, DNS tunnel) — deferred to a later sprint that swaps mocks for real implementations behind the same protocols.
- DNS Protection functionality (tunnel, VPN configuration) — screen/IA only.
- YouTube web extension screens/entry points — not part of the confirmed Stitch screen inventory; add to IA only if/when designed.
- Snapshot or UI automation testing.
