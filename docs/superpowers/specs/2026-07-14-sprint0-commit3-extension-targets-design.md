# Sprint 0 — Commit 3: Extension Targets Design

**Project:** ADBLX (SHIELD) — iOS Ad Blocker
**Status:** Approved (Revision 1)
**Parent spec:** `docs/superpowers/specs/2026-07-14-sprint0-bootstrap-design.md`

## Goal

Add all 6 placeholder extension targets to `project.yml` — 4 Content Blockers (`ADBLXAdsBlocker`, `ADBLXPrivacyBlocker`, `ADBLXAnnoyancesBlocker`, `ADBLXRegionalBlocker`), `ADBLXPacketTunnel`, `ADBLXSafariWebExtension` — building successfully with zero business logic and zero capabilities/entitlements. This commit establishes target topology only.

## Sprint 0's three-commit separation of concerns

- **Commit 3 (this one):** target topology — do the targets exist, do they build.
- **Commit 4:** permissions — App Groups, Network Extension entitlement, Web Extension capabilities.
- **Commit 5:** functionality — real bundled rule snapshots, `reloadContentBlocker()`, runtime verification.

Each commit answers exactly one question. This commit must not blur into Commit 4 or 5's territory.

## Target creation strategy

All 6 targets added in one commit. They are pure placeholders with no interdependencies, so splitting into multiple commits adds process overhead without reducing risk.

## Product type & Info.plist (grounded in Xcode 26.6 investigation)

Every extension target uses `type: app-extension`. Confirmed directly from Xcode 26.6's shipped `App Extension Base.xctemplate` (`Applications/Xcode.app/Contents/Developer/Library/Xcode/Templates/Project Templates/Base/App Extension Base.xctemplate/TemplateInfo.plist`): `ProductType: com.apple.product-type.app-extension`. XcodeGen has no special "content blocker"/"packet tunnel"/"safari extension" target type — differentiation is entirely via the `NSExtension` Info.plist dictionary.

**Each target's Info.plist is generated by XcodeGen's `info.properties` in `project.yml` — no physical `Info.plist` files are checked in.** This keeps `project.yml` as Commit 2's established single source of truth. Rule: physical `Info.plist` files are not permitted for these targets unless XcodeGen cannot express a required key; any exception requires a new ADR.

| Target | `NSExtensionPointIdentifier` | Principal class |
|---|---|---|
| `ADBLXAdsBlocker` / `ADBLXPrivacyBlocker` / `ADBLXAnnoyancesBlocker` / `ADBLXRegionalBlocker` | `com.apple.Safari.content-blocker` | `$(PRODUCT_MODULE_NAME).ContentBlockerRequestHandler` |
| `ADBLXPacketTunnel` | `com.apple.networkextension.packet-tunnel` | `$(PRODUCT_MODULE_NAME).PacketTunnelProvider` |
| `ADBLXSafariWebExtension` | `com.apple.Safari.web-extension` | `$(PRODUCT_MODULE_NAME).SafariWebExtensionHandler` |

**Investigation note:** the Safari Web Extension identifier and principal class are verified directly against a live Xcode 26.6 template (`iOS Safari Extension.xctemplate`), including `OTHER_LDFLAGS = -framework SafariServices`. The Content Blocker and Packet Tunnel identifiers could not be verified the same way — Apple removed the dedicated project-creation templates for these two types in recent Xcode versions (superseded in the target-creation UI by the newer ExtensionKit "Generic Extension" template for some extension categories, though Content Blockers and Network Extensions are not ExtensionKit-based and are unaffected by that migration). These two identifiers are long-stable, unchanged Apple API surface independent of the template system. Residual risk is low and self-limiting: a wrong identifier fails to build or fails Info.plist validation (acceptance criterion 4), so it cannot silently pass this commit.

## Placeholder depth per target type

### Content Blockers (×4)

`ContentBlockerRequestHandler: NSObject, NSExtensionRequestHandling` implements `beginRequest(with:)` following the **real** content-blocker request lifecycle, not a stub:

1. Locate the bundled `Resources/blockerList.json` in the extension's bundle.
2. Wrap it in an `NSItemProvider` with the `public.json` UTI.
3. Complete the request via `context.completeRequest(returningItems: [NSExtensionItem(attachments: [itemProvider])], completionHandler: nil)`.

`Resources/blockerList.json` contains `[]` in this commit — a syntactically valid, empty rule list. **No code calls `SFContentBlockerManager.reloadContentBlocker()` anywhere in this commit.** Commit 5 changes exactly one thing: `[]` becomes a real 1–3K compiled rule set. The handler's request-handling logic does not change between Commit 3 and Commit 5 — only the JSON payload does.

The JSON is loaded from the extension bundle, **not** the App Group container. By Commit 5 the app begins writing rule data into the App Group; Commit 3 intentionally exercises only the bundled-resource path, not App Group I/O.

### PacketTunnel

`PacketTunnelProvider: NEPacketTunnelProvider` implements only the overrides required by the SDK (`startTunnel(options:completionHandler:)`, `stopTunnel(with:completionHandler:)`, `handleAppMessage(_:completionHandler:)`). Every implementation calls its completion handler immediately (e.g. `completionHandler(nil)` / `completionHandler(nil)`) with no other work: no timers, no observers, no networking, no file I/O. No Network Extension entitlement (Commit 4).

### Safari Web Extension

`SafariWebExtensionHandler: NSObject, NSExtensionRequestHandling` — native messaging stub matching Xcode's own template shape. Resources mirror Apple's template structure:

```
Extensions/ADBLXSafariWebExtension/
    SafariWebExtensionHandler.swift
    Resources/
        manifest.json
        background.js
        _locales/
            en/
                messages.json
```

`manifest.json` is a baseline Manifest V2/V3 declaration with no permissions beyond what Xcode's own template ships. `background.js` is a stub. `messages.json` contains a placeholder locale entry. No popup, no content script — trimmed to the minimum that produces a structurally valid, loadable web extension bundle.

## Folder ownership

```
Extensions/
    ADBLXAdsBlocker/{ContentBlockerRequestHandler.swift, Resources/blockerList.json}
    ADBLXPrivacyBlocker/{ContentBlockerRequestHandler.swift, Resources/blockerList.json}
    ADBLXAnnoyancesBlocker/{ContentBlockerRequestHandler.swift, Resources/blockerList.json}
    ADBLXRegionalBlocker/{ContentBlockerRequestHandler.swift, Resources/blockerList.json}
    ADBLXPacketTunnel/PacketTunnelProvider.swift
    ADBLXSafariWebExtension/{SafariWebExtensionHandler.swift, Resources/manifest.json, Resources/background.js, Resources/_locales/en/messages.json}
```

Each folder uses `type: syncedFolder` sourcing (consistent with Commit 2's approach for `ADBLX`/`ADBLXTests`/`ADBLXUITests`). Each target owns only its own folder — no shared source files between extensions in this commit. `Packages/ADBLXShared` linkage remains gated on ADR-0003 (unrelated to and unaffected by this commit).

## Capabilities — explicitly excluded

No App Groups, no Network Extension entitlement, no Web Extension capabilities. All 6 new targets get `CODE_SIGN_STYLE: Automatic` and nothing else capability-related. This is Commit 4's job entirely.

## Acceptance criteria

1. `xcodegen generate` succeeds; running it twice produces no further diff (same idempotency check as Commit 2).
2. All 7 targets/schemes (`ADBLX` + 6 extensions) appear in Xcode with no missing file references, no yellow/orange folders, no migration prompts.
3. `xcodebuild build` succeeds for every target — the app and all 6 extensions.
4. For each extension, both:
   - `plutil -lint` on the generated `Info.plist` passes (structurally valid plist), and
   - `plutil -p` on the same file confirms `NSExtension` exists with the correct `NSExtensionPointIdentifier`, the expected `NSExtensionPrincipalClass`, and no unexpected keys.
5. No entitlement/capability warnings in Xcode's project navigator for any target.
6. No runtime verification — no simulator launch of any extension, no `SFContentBlockerManager` calls, no tunnel start. Entirely Commit 5's job.
7. After generation, run a clean `xcodebuild build` and record wall-clock time as an informal new build-time baseline (7 targets vs. 3) — not a gate, just a note for later performance tracking once `Performance/Baselines.md` is populated in Commit 5.

## Performance & battery

Expected to be effectively zero measurable runtime cost: no main-thread work beyond extension initialization, negligible memory (placeholder handlers do almost no work), no network activity, no App Group I/O, no background execution. No persistent background processes are introduced in this commit — PacketTunnel and the Web Extension existing as targets does not imply any background execution; their placeholder implementations correctly avoid it. The only real-world impact is a compile-time increase from 3 targets to 7, tracked informally per acceptance criterion 7.
