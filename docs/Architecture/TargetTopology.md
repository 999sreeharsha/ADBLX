# Target Topology

**Status:** current as of Sprint 0 Commit 5 (Sprint 0 complete). Living document — update in place as targets, build settings, or capabilities change. For the "why" behind these decisions, see the linked specs; this document covers only the "how it currently works."

## Build system

The project is generated from `project.yml` via [XcodeGen](https://github.com/yonaskolb/XcodeGen) (2.45.4+). **`ADBLX.xcodeproj` is a build artifact, not a source of truth** — never hand-edit it. To make any project-structure change: edit `project.yml`, run `xcodegen generate`, commit both. See [`README.md`](../../README.md) for the quickstart.

- Project-level build settings (compiler warnings, `CLANG_*`/`GCC_*`, Debug/Release differences) live in `Config/Base.xcconfig`, `Config/Debug.xcconfig`, `Config/Release.xcconfig`, wired in via `project.yml`'s `configFiles:`.
- Target-level settings (bundle ID, deployment targets, capabilities) are declared inline per target in `project.yml`.
- All source folders use XcodeGen's `type: syncedFolder`, matching Xcode 16's `PBXFileSystemSynchronizedRootGroup` — the project file's group structure always mirrors the filesystem, no explicit file lists to maintain.
- The `ADBLX` target declares all 6 extensions as `dependencies:` with `embed: true`, so XcodeGen generates the Embed App Extensions build phase copying each `.appex` into `ADBLX.app/PlugIns/`. Without this, extensions build standalone (as Commits 3–4's CI does) but are never actually part of the installed app and are invisible to Safari/Settings — this was fixed in Commit 5 after discovering the app previously shipped with an empty `PlugIns/` folder.
- Every extension target's `Info.plist` is generated by XcodeGen from `project.yml`'s `info.properties` — there are no hand-authored physical `Info.plist` files in the repo. Rule: this stays true unless XcodeGen genuinely cannot express a required key, and any exception requires a new ADR.
- Scheme generation is **not** left to XcodeGen's default (`options.autogenerateSchemes: false`). Exactly one scheme, `ADBLX`, is explicitly defined in `project.yml`, matching the single-scheme model of the original hand-authored project. It builds the app plus all 6 extensions, and its Test action runs `ADBLXTests` + `ADBLXUITests`.
  - Note: Xcode's own per-developer "Autocreate schemes" IDE preference (unrelated to `project.yml`) will still show ephemeral per-target schemes in the scheme selector UI for anyone with that preference on. This is normal, unavoidable, and does not get written to `xcshareddata/` unless someone explicitly saves it — the committed project has exactly one shared scheme.

## Multiplatform scope

The project targets **iOS, native macOS, and visionOS simultaneously** on a single multi-destination target (`platform: auto`, `supportedDestinations: [iOS, macOS, visionOS]`), not Mac via Catalyst as earlier documentation (`agent.md`) described. This was inherited as-is from the original Xcode-generated scaffold and deliberately preserved (not decided) through the XcodeGen migration — narrowing or confirming this scope is an open item for a future Platform Strategy ADR, not yet written.

## Targets (7 total)

| Target | Type | Product type | Bundle ID | Purpose |
|---|---|---|---|---|
| `ADBLX` | App | `application` | `com.ADBLX.ADBLX` | Main app |
| `ADBLXAdsBlocker` | Content Blocker | `app-extension` | `com.ADBLX.ADBLX.AdsBlocker` | Ads filter list |
| `ADBLXPrivacyBlocker` | Content Blocker | `app-extension` | `com.ADBLX.ADBLX.PrivacyBlocker` | Privacy/tracker filter list |
| `ADBLXAnnoyancesBlocker` | Content Blocker | `app-extension` | `com.ADBLX.ADBLX.AnnoyancesBlocker` | Cookie banners/annoyances filter list |
| `ADBLXRegionalBlocker` | Content Blocker | `app-extension` | `com.ADBLX.ADBLX.RegionalBlocker` | Regional (India) filter list |
| `ADBLXPacketTunnel` | Network Extension | `app-extension` | `com.ADBLX.ADBLX.PacketTunnel` | On-device DNS tunnel (premium) |
| `ADBLXSafariWebExtension` | Safari Web Extension | `app-extension` | `com.ADBLX.ADBLX.SafariWebExtension` | YouTube-in-Safari + cosmetic filtering (premium) |
| `ADBLXTests` | Unit test | `bundle.unit-test` | `com.ADBLX.ADBLXTests` | Hosted by `ADBLX` |
| `ADBLXUITests` | UI test | `bundle.ui-testing` | `com.ADBLX.ADBLXUITests` | Hosted by `ADBLX` |

**Bundle ID note:** the app and its two test targets use `com.ADBLX.<TargetName>`, inherited from the original Xcode scaffold. Extensions use `com.ADBLX.ADBLX.<Suffix>` (the app's bundle ID, `com.ADBLX.ADBLX`, plus a dotted suffix) — this nesting is a hard iOS requirement (an app extension's bundle ID must have the container app's bundle ID as a dotted prefix), not a style choice; installs fail with "Mismatched bundle IDs" otherwise. This was discovered and fixed in Commit 5 — Commits 3–4 only ever built the extension targets standalone via CI, which doesn't exercise embedding or installation, so the violation went unnoticed until an app with embedded extensions was actually installed on a simulator/device. Neither of these is the `com.sreeharsha.adblx.*` convention originally proposed in Sprint 0 planning; normalizing to that convention (while preserving the same nesting rule) is deferred to a future ADR — not yet written.

### Extension mechanism

All 6 extensions are the same underlying product type, `com.apple.product-type.app-extension` — there is no XcodeGen-specific "content blocker" or "packet tunnel" target type. They're differentiated purely by their generated `Info.plist`'s `NSExtension` dictionary:

| Target(s) | `NSExtensionPointIdentifier` | `NSExtensionPrincipalClass` |
|---|---|---|
| 4 Content Blockers | `com.apple.Safari.content-blocker` | `$(PRODUCT_MODULE_NAME).ContentBlockerRequestHandler` |
| `ADBLXPacketTunnel` | `com.apple.networkextension.packet-tunnel` | `$(PRODUCT_MODULE_NAME).PacketTunnelProvider` |
| `ADBLXSafariWebExtension` | `com.apple.Safari.web-extension` | `$(PRODUCT_MODULE_NAME).SafariWebExtensionHandler` |

These identifiers are stable, long-standing Apple API surface, verified where possible directly against Xcode 26.6's own shipped extension templates (see the Commit 3 design spec for the investigation details).

## Folder layout

```
ADBLX/                          App source (synced folder)
ADBLXTests/                     Unit tests (synced folder)
ADBLXUITests/                   UI tests (synced folder)
Extensions/
    ADBLXAdsBlocker/
        ContentBlockerRequestHandler.swift
        Resources/blockerList.json   ([] — placeholder, real rules land in a later commit)
        Info.plist                   (generated by XcodeGen — do not hand-edit)
    ADBLXPrivacyBlocker/          (same shape as ADBLXAdsBlocker)
    ADBLXAnnoyancesBlocker/       (same shape as ADBLXAdsBlocker)
    ADBLXRegionalBlocker/         (same shape as ADBLXAdsBlocker)
    ADBLXPacketTunnel/
        PacketTunnelProvider.swift
        Info.plist
    ADBLXSafariWebExtension/
        SafariWebExtensionHandler.swift
        Resources/manifest.json, background.js, _locales/en/messages.json
        Info.plist
Config/                          Base/Debug/Release.xcconfig — project-level settings only
Packages/ADBLXShared/            Empty skeleton — gated on ADR-0003 (not yet written)
```

Each extension target owns only its own folder; there are no shared source files between extensions yet (that's what `Packages/ADBLXShared` is reserved for, once ADR-0003 is approved).

## Content Blocker request lifecycle

Each `ContentBlockerRequestHandler.beginRequest(with:)` implements the **real** production lifecycle already, not a stub: it wraps a rules JSON file in an `NSItemProvider` and completes the request via `NSExtensionContext.completeRequest`. `ADBLXAdsBlocker` (migrated in Commit 5) resolves that file from the App Group container first (`Rules/Ads.json`), falling back to its own bundled `Resources/blockerList.json` (70 hand-authored synthetic rules) if the App Group copy doesn't exist yet. `ADBLXPrivacyBlocker`/`ADBLXAnnoyancesBlocker`/`ADBLXRegionalBlocker` are unmigrated — their JSON still contains `[]` and is read only from the bundle. A later commit changes their payload and replicates the App Group + fallback pattern — the handler code shape doesn't need to change.

## App Groups

Identifier: `group.com.ADBLX.shared` — follows the `com.ADBLX.*` bundle ID namespace, not the earlier-proposed-but-superseded `com.sreeharsha.adblx` convention (see bundle ID note above).

| Target | App Group |
|---|---|
| `ADBLX` | ✅ |
| `ADBLXAdsBlocker` | ✅ |
| `ADBLXPrivacyBlocker` | ✅ |
| `ADBLXAnnoyancesBlocker` | ✅ |
| `ADBLXRegionalBlocker` | ✅ |
| `ADBLXSafariWebExtension` | ✅ |
| `ADBLXPacketTunnel` | ⏸ Deferred — see "Development environment limitations" |
| `ADBLXTests` / `ADBLXUITests` | ❌ Not needed |

Configured via `entitlements:` in `project.yml` per target, generating a `.entitlements` file at build time (same generated-artifact pattern as `Info.plist` — never hand-authored). `REGISTER_APP_GROUPS: YES` is set alongside on each entitled target so Automatic signing registers the capability with the App ID.

`AppGroup.swift` exposes the identifier as `AppGroup.identifier`, duplicated in exactly 2 places: `ADBLX/AppGroup.swift` (app target) and `Extensions/ADBLXAdsBlocker/AppGroup.swift` (the one extension migrated to read from the App Group in Commit 5). No `Packages/ADBLXShared` linkage yet (still gated on unwritten ADR-0003); revisit if a third target needs it.

`ADBLXAdsBlocker` is the only Content Blocker reading from the App Group (`Rules/Ads.json`, with a permanent bundle-resource fallback) — see `ContentBlockerRequestHandler.swift`. `ADBLXPrivacyBlocker`/`ADBLXAnnoyancesBlocker`/`ADBLXRegionalBlocker` still bundle `[]` and are unmigrated; replicating the pattern to them is future work.

`ContentBlockerBootstrap` (`ADBLX/ContentBlockerBootstrap.swift`) runs on every launch, dispatched off the main actor from `ADBLXApp`. Its rule copy is idempotent (checks whether `Rules/Ads.json` already exists before copying), but it calls `SFContentBlockerManager.reloadContentBlocker(withIdentifier:)` unconditionally on every launch — a **Sprint-0-only** stand-in (documented via a code comment) for the missing "extension was just enabled in Safari" signal Apple doesn't expose; Sprint 1's manifest/version-comparison logic replaces this with reload-only-on-change. Logging uses `os.Logger`, subsystem `com.ADBLX.ADBLX`, categories `Bootstrap`/`AppGroup`/`MetricKit`.

### Shared container contract

Directory structure inside the App Group container (contract only — not yet exercised with real I/O; that's Commit 5):

```
group.com.ADBLX.shared/
├── Rules/
│   ├── Ads.json
│   ├── Privacy.json
│   ├── Annoyances.json
│   └── Regional.json
├── Manifest/
│   └── manifest.json
├── Metadata/
│   ├── installed-versions.json
│   └── manifest-state.json
└── Diagnostics/
```

`Rules/` holds active rule JSON regardless of provenance (bundled/compiled/imported) — Content Blockers will eventually read from here instead of their bundled `Resources/blockerList.json`. Files are written atomically by the main app (`.tmp` → rename) so extensions never observe partially-written rule files.

## Development environment limitations

Current development uses an Apple Personal Team (free, non-paid). Therefore:

- The Network Extension entitlement (`com.apple.developer.networking.networkextension`) is unavailable — Personal Teams cannot provision it.
- `ADBLXPacketTunnel`'s capability and App Group are intentionally deferred as a result.
- This is an Apple provisioning limitation, not a project or architecture limitation. Revisit once the account upgrades to a paid Apple Developer Program membership.

## Continuous Integration

`.github/workflows/ci.yml` runs on push/PR to `dev`/`main` plus manual dispatch: checkout → select latest-stable Xcode → install XcodeGen → `xcodegen generate` → drift check (`git diff --exit-code`) → build the `ADBLX` scheme → run `ADBLXTests` only. `ADBLXUITests` is intentionally excluded — there is no UI worth testing yet, not because of flakiness; it joins CI once onboarding/settings screens exist.

## What's deliberately not here yet

- **Network Extension entitlement** — `ADBLXPacketTunnel` has no capability configured; blocked on the Personal Team limitation (see "Development environment limitations" above).
- **CI caching, build artifacts, release automation** — `.github/workflows/ci.yml` (added Commit 4) runs generate/drift-check/build/unit-test only.
- **Runtime verification of the other 5 extensions** — Commit 5 verified `ADBLXAdsBlocker` end-to-end (embedded, installed, App Group round-trip, `reloadContentBlocker()`); the other 3 Content Blockers, `ADBLXPacketTunnel`, and `ADBLXSafariWebExtension` are embedded and build, but have no runtime behavior exercised yet.
- **`Packages/ADBLXShared` source code** — the directory exists but is empty; linking it into any target is gated on ADR-0003.
