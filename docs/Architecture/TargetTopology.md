# Target Topology

**Status:** current as of Sprint 2 (update pipeline complete). Living document — update in place as targets, build settings, or capabilities change. For the "why" behind these decisions, see the linked specs; this document covers only the "how it currently works."

## Build system

The project is generated from `project.yml` via [XcodeGen](https://github.com/yonaskolb/XcodeGen) (2.45.4+). **`ADBLX.xcodeproj` is a build artifact, not a source of truth** — never hand-edit it. To make any project-structure change: edit `project.yml`, run `xcodegen generate`, commit both. See [`README.md`](../../README.md) for the quickstart.

- Project-level build settings (compiler warnings, `CLANG_*`/`GCC_*`, Debug/Release differences) live in `Config/Base.xcconfig`, `Config/Debug.xcconfig`, `Config/Release.xcconfig`, wired in via `project.yml`'s `configFiles:`.
- `DEVELOPMENT_TEAM` (`93F78RF6FG`, the Personal Team for `sreeharsha999@icloud.com`) is declared once in `project.yml`'s top-level `settings.base`, so every target inherits it through Xcode's standard build-setting resolution — confirmed via `xcodebuild -showBuildSettings` on multiple targets. It is **not** set anywhere in the generated `project.pbxproj` on disk after `xcodegen generate` for any individual target; only the project-level Debug/Release configs carry it, by design. Before this was added, Team had to be manually re-selected in Xcode's Signing & Capabilities per target, and any subsequent `xcodegen generate` (which happens on every `project.yml` change) silently wiped it again — the same Team ID isn't secret (it ships inside every provisioning profile and signed binary anyway), so committing it directly here is intentional, not an oversight.
- Target-level settings (bundle ID, deployment targets, capabilities) are declared inline per target in `project.yml`.
- All source folders use XcodeGen's `type: syncedFolder`, matching Xcode 16's `PBXFileSystemSynchronizedRootGroup` — the project file's group structure always mirrors the filesystem, no explicit file lists to maintain.
- The `ADBLX` target declares all 6 extensions as `dependencies:` with `embed: true`, so XcodeGen generates the Embed App Extensions build phase copying each `.appex` into `ADBLX.app/PlugIns/`. Without this, extensions build standalone (as Commits 3–4's CI does) but are never actually part of the installed app and are invisible to Safari/Settings — this was fixed in Commit 5 after discovering the app previously shipped with an empty `PlugIns/` folder.
- Every extension target's `Info.plist` is generated by XcodeGen from `project.yml`'s `info.properties` — there are no hand-authored physical `Info.plist` files in the repo. Rule: this stays true unless XcodeGen genuinely cannot express a required key, and any exception requires a new ADR.
- Scheme generation is **not** left to XcodeGen's default (`options.autogenerateSchemes: false`). Exactly one scheme, `ADBLX`, is explicitly defined in `project.yml`, matching the single-scheme model of the original hand-authored project. It builds the app plus all 6 extensions, and its Test action runs `ADBLXTests` + `ADBLXUITests`.
  - Note: Xcode's own per-developer "Autocreate schemes" IDE preference (unrelated to `project.yml`) will still show ephemeral per-target schemes in the scheme selector UI for anyone with that preference on. This is normal, unavoidable, and does not get written to `xcshareddata/` unless someone explicitly saves it — the committed project has exactly one shared scheme.

## Multiplatform scope

The project targets **iOS, native macOS, and visionOS simultaneously** on a single multi-destination target (`platform: auto`, `supportedDestinations: [iOS, macOS, visionOS]`), not Mac via Catalyst as earlier documentation (`agent.md`) described. This was inherited as-is from the original Xcode-generated scaffold and deliberately preserved (not decided) through the XcodeGen migration — narrowing or confirming this scope is an open item for a future Platform Strategy ADR, not yet written.

### Extension mechanism

All 6 extensions are the same underlying product type, `com.apple.product-type.app-extension` — there is no XcodeGen-specific "content blocker" or "packet tunnel" target type. They're differentiated purely by their generated `Info.plist`'s `NSExtension` dictionary:

| Target(s) | `NSExtensionPointIdentifier` | `NSExtensionPrincipalClass` |
|---|---|---|
| 4 Content Blockers | `com.apple.Safari.content-blocker` | `$(PRODUCT_MODULE_NAME).ContentBlockerRequestHandler` |
| `ADBLXPacketTunnel` | `com.apple.networkextension.packet-tunnel` | `$(PRODUCT_MODULE_NAME).PacketTunnelProvider` |
| `ADBLXSafariWebExtension` | `com.apple.Safari.web-extension` | `$(PRODUCT_MODULE_NAME).SafariWebExtensionHandler` |

These identifiers are stable, long-standing Apple API surface, verified where possible directly against Xcode 26.6's own shipped extension templates (see the Commit 3 design spec for the investigation details).

## Content Blocker request lifecycle

Each `ContentBlockerRequestHandler.beginRequest(with:)` implements the **real** production lifecycle already, not a stub: it wraps a rules JSON file in an `NSItemProvider` and completes the request via `NSExtensionContext.completeRequest`. `ADBLXAdsBlocker` resolves that file from the App Group container first — **`Compiled/Ads.json`** as of Sprint 1 (was `Rules/Ads.json` in Sprint 0; the extension's read path was updated in Sprint 1 Task 12 to match where `FilterStore`/`FilterPipeline` actually write) — falling back to its own bundled `Resources/blockerList.json` (70 hand-authored synthetic rules) if the App Group copy doesn't exist yet. `ADBLXPrivacyBlocker`/`ADBLXAnnoyancesBlocker`/`ADBLXRegionalBlocker` are still unmigrated — their JSON still contains `[]` and is read only from the bundle. A later sprint changes their payload and replicates the App Group + fallback pattern — the handler code shape doesn't need to change.

**Rule resolution order** (`ADBLXAdsBlocker` only, evaluated fresh on every `beginRequest`):

```
1. App Group container — Compiled/Ads.json   (if present, use it)
2. Bundle resource      — blockerList.json   (fallback if (1) is missing)
3. Safari compiles the returned JSON into its content-blocking engine
```

Rationale: the App Group path exists so the rule pipeline (Sprint 1) and the networked update pipeline (Sprint 2, via `UpdateCoordinator`) can drop fresh compiled rules into the shared container without shipping a new app build — that's the entire point of `Compiled/` being writable at runtime by `FilterPipeline`. The bundle fallback exists for two cases the App Group path can't cover on its own: first launch, before `ContentBlockerBootstrap` has ever run (though in practice it always runs before Safari can reach the extension, since the extension can't be enabled until the app has been installed and launched at least once), and recovery if the App Group file is ever missing or corrupted for any reason. Both paths are logged (`os.Logger`, subsystem `com.ADBLX.ADBLX`, category `AppGroup`) with the rule count actually loaded, so which path served a given request is always visible in Console.app/`log show` without inspecting the filesystem.

## App Groups

Identifier: `group.com.ADBLX.shared` — follows the `com.ADBLX.*` bundle ID namespace, not the earlier-proposed-but-superseded `com.sreeharsha.adblx` convention (see bundle ID note above).

| Target | App Group |
|---|---|
| `ADBLX` | ✅ |
| `ADBLXAdsBlocker` | ✅ |
| `ADBLXPrivacyBlocker` | ✅ |
| `ADBLXAnnoyancesBlocker` | ✅ |
| `ADBLXRegionalBlocker` | ✅ |
| `ADBLXSafariWebExtension` | ✅ |
| `ADBLXPacketTunnel` | ⏸ Deferred — see "Development environment limitations" |
| `ADBLXTests` / `ADBLXUITests` | ❌ Not needed |

Configured via `entitlements:` in `project.yml` per target, generating a `.entitlements` file at build time (same generated-artifact pattern as `Info.plist` — never hand-authored). `REGISTER_APP_GROUPS: YES` is set alongside on each entitled target so Automatic signing registers the capability with the App ID.

`AppGroup.swift` exposes the identifier as `AppGroup.identifier`, duplicated in exactly 2 places: `ADBLX/AppGroup.swift` (app target) and `Extensions/ADBLXAdsBlocker/AppGroup.swift` (the one extension migrated to read from the App Group). No `Packages/ADBLXShared` linkage yet (still gated on unwritten ADR-0003); revisit if a third target needs it.

`ADBLXAdsBlocker` is the only Content Blocker reading from the App Group (`Compiled/Ads.json` as of Sprint 1, with a permanent bundle-resource fallback) — see `ContentBlockerRequestHandler.swift`. `ADBLXPrivacyBlocker`/`ADBLXAnnoyancesBlocker`/`ADBLXRegionalBlocker` still bundle `[]` and are unmigrated; replicating the pattern to them is future work.

As of Sprint 1, **`FilterStore` (`ADBLX/Filtering/Storage/FilterStore.swift`) is the sole type in the main app permitted to call `containerURL(forSecurityApplicationGroupIdentifier:)` directly** — enforced by a grep check run at the end of Sprint 1 Task 11 and independently re-verified in the final whole-branch review. Every other type that needs App Group filesystem access routes through `FilterStore`'s `read`/`writeMetadata`/`directoryURL` API instead of touching `FileManager` itself. The one documented exception is `ADBLXAdsBlocker`'s own extension-side read path (`ContentBlockerRequestHandler.swift`), which is intentionally outside `FilterStore`'s main-app-only scope — extensions have their own minimal, read-only container access and cannot host `FilterStore`'s actor.

`ContentBlockerBootstrap` (`ADBLX/ContentBlockerBootstrap.swift`) runs on every launch, dispatched off the main actor from `ADBLXApp` via `Task.detached`. As of Sprint 1 it no longer touches `FileManager` or `SFContentBlockerManager` directly — Sprint 0's two methods (`ensureInitialRulesInstalled()` / `reloadIfNeeded()`) were retired and replaced with a single `nonisolated static func ensureInitialRulesInstalled(pipeline: FilterPipeline) async -> Bool` that delegates entirely into `FilterPipeline.installBundledSnapshotIfNeeded()`. The pipeline itself is constructed once via `AppCompositionRoot.makeFilterPipeline()` (dependency injection, no singleton) and reinstalls the bundled snapshot on every launch — unchanged since Sprint 1. Reload-only-on-change against a fetched manifest now exists as a capability (`UpdatePlanner`'s `.keep` case, Sprint 2), but `ContentBlockerBootstrap` itself doesn't use it — see the blocking risk noted just below. Logging uses `os.Logger`, subsystem `com.ADBLX.ADBLX`, categories `Bootstrap`/`AppGroup`/`MetricKit`.

**Sprint 2 blocking risk, not yet reachable:** `ContentBlockerBootstrap`'s unconditional reinstall-on-every-launch is still exactly the Sprint 1 behavior described above — nothing in Sprint 2 calls it differently, and nothing yet calls `UpdateCoordinator.run()` either, so the two paths never collide today. The moment a future launch path calls `UpdateCoordinator.run()` *in addition to* (not *instead of*) the bootstrap call, the sequence becomes: update installs a real filter → app relaunches → bootstrap unconditionally overwrites `Compiled/Ads.json`/`installed_filters.json` back to the bundled snapshot → the update is silently reverted. Whoever wires up the first real caller of `run()` must gate `installBundledSnapshotIfNeeded()` behind "no update has ever succeeded" (e.g. skip it if `ManifestStore.load()` returns non-nil) or remove the unconditional bootstrap call entirely.

As of Sprint 2, `FilterStore` additionally exposes `snapshotForRollback()`/`restore(_:)` — copies `Compiled/`/`Metadata/` into a transient `Previous/` root before a batch update begins, and can replace current contents with that snapshot (including removing files created after the snapshot) if the batch fails partway. `UpdateCoordinator` (`ADBLX/Filtering/Updates/UpdateCoordinator.swift`) is the sole caller of both, and the sole actor orchestrating a full update transaction: fetch `manifest.json` (honoring ETag/304 via `ManifestClient`) → diff against `installed_filters.json` via `UpdatePlanner` → download every `.install` entry (`FilterDownloadClient`) → verify every download's checksum (`Checksum.verify`) before touching the App Group at all → snapshot → install each verified filter through `FilterPipeline.install(..., reloadStrategy: .deferred)` → commit the new manifest+ETag (`ManifestStore`) → exactly one `ReloadCoordinator.reload` across the affected extensions. Any failure after the snapshot triggers `restore(_:)`; if `restore` itself fails, `run()` returns `.rollbackFailed(originalReason:restoreError:)` rather than throwing — the `Previous/` snapshot is left on disk in that case rather than deleted, since `restore()` only removes it after both directory replacements succeed.

`ReloadCoordinator` (`ADBLX/Filtering/Deployment/ReloadCoordinator.swift`) is now the **sole call site** for `SFContentBlockerManager.reloadContentBlocker(withIdentifier:)` in the main app — also grep-enforced and independently re-verified. It bounds every reload call with a timeout (default 10s): `SFContentBlockerManager`'s completion handler has no documented upper bound, and an extension that's never been enabled in Safari Settings can leave the callback hanging forever (this caused a multi-hour Sprint 0 debugging incident — see the bundle-ID-nesting issue below). The fix races the real callback against an *unstructured* `Task` timer, not a `TaskGroup` child (which would implicitly await the stuck callback anyway), guarded by a single-resume lock. **Known gap, accepted as-is:** no test currently forces the timeout branch to actually fire — the two existing tests both hit the fast-callback path. Closing this would need an injectable reload seam not in the current design; not a blocker for Sprint 1 or Sprint 2, tracked as future follow-up.

### Shared container contract

Directory structure inside the App Group container, as actually implemented and exercised by `FilterStore`/`FilterPipeline`/`UpdateCoordinator` (Sprint 2 — this supersedes the pre-implementation contract sketch from Commit 4):

```
group.com.ADBLX.shared/
├── Filters/       Raw/normalized filter source data (still unused — reserved for a future
│                  normalize stage, not part of Sprint 1 or Sprint 2)
├── Compiled/
│   └── Ads.json           Partitioned, compiled JSON ready for ADBLXAdsBlocker to read
│                           (filename convention: Compiled/<FilterGroup rawValue, capitalized>.json —
│                           only Ads.json exists this sprint, one partition per FilterPipeline.install() call)
├── Metadata/
│   ├── installed_filters.json   [InstalledFilter] — accumulated by id as of Sprint 2
│   │                             (was single-entry overwrite in Sprint 1)
│   ├── manifest.json             CachedManifest (FilterManifest + ETag) — Sprint 2, via ManifestStore
│   └── statistics.json          RuleStatistics — counts/durations/sizes only, never rule content
└── Previous/      Transient rollback snapshot root (Compiled/, Metadata/ copies) — Sprint 2.
                    Only exists during an UpdateCoordinator batch; created by
                    snapshotForRollback(), consumed and deleted by a successful restore(_:).
                    Left on disk (not deleted) if restore(_:) itself fails.
```

All directories are created on demand by `FilterStore` (idempotent, no separate provisioning step). `Compiled/*.json` is written exclusively through `AtomicRuleWriter` (write-to-temp in the same directory → `fsync(F_FULLFSYNC)` → `rename(2)`), so `ADBLXAdsBlocker` never observes a partially-written file — on any failure mid-write, the previously-committed file is left completely untouched and the temp file is cleaned up. `Metadata/*.json` files go through `FilterStore.writeMetadata`, a simpler non-atomic write (small files, low update frequency) — deliberately **not** used for `Compiled/` output, which always needs the atomic guarantee.

The original planned `Diagnostics/` directory from the Commit 4 sketch still doesn't exist — there's no separate diagnostics sink beyond `Metadata/statistics.json` and `os.Logger`. This is a deliberate scope line, not a dropped requirement.

## Development environment limitations

Current development uses an Apple Personal Team (free, non-paid). Therefore:

- The Network Extension entitlement (`com.apple.developer.networking.networkextension`) is unavailable — Personal Teams cannot provision it.
- `ADBLXPacketTunnel`'s capability and App Group are intentionally deferred as a result.
- This is an Apple provisioning limitation, not a project or architecture limitation. Revisit once the account upgrades to a paid Apple Developer Program membership.

## Continuous Integration

`.github/workflows/ci.yml` runs on push/PR to `dev`/`main` plus manual dispatch: checkout → select latest-stable Xcode → install XcodeGen → `xcodegen generate` → drift check (`git diff --exit-code`) → build the `ADBLX` scheme → run `ADBLXTests` only. `ADBLXUITests` is intentionally excluded — there is no UI worth testing yet, not because of flakiness; it joins CI once onboarding/settings screens exist.

## What's deliberately not here yet

- **Network Extension entitlement** — `ADBLXPacketTunnel` has no capability configured; blocked on the Personal Team limitation (see "Development environment limitations" above).
- **CI caching, build artifacts, release automation** — `.github/workflows/ci.yml` (added Commit 4) runs generate/drift-check/build/unit-test only.
- **Runtime verification of the other 5 extensions** — Sprint 0/1 verified `ADBLXAdsBlocker` end-to-end (embedded, installed, App Group round-trip, `reloadContentBlocker()`, and now the full `FilterPipeline` write path); the other 3 Content Blockers, `ADBLXPacketTunnel`, and `ADBLXSafariWebExtension` are embedded and build, but have no runtime behavior exercised yet.
- **`Packages/ADBLXShared` source code** — the directory exists but is empty; linking it into any target is gated on ADR-0003.
- **Real rule compilation** — `RuleCompiler`'s only implementation, `PassthroughRuleCompiler`, treats source as already-valid Safari JSON and passes it through with count-only statistics. A SafariConverterLib-backed real compiler is gated on ADR-0001 (GPL-3.0 licensing decision, not yet written); the protocol boundary means that swap only ever touches `ADBLX/Filtering/Compilation/`.
- **Multi-filter / non-Ads groups in the pipeline** — `PassthroughAdsPartitioner` only ever produces an `Ads` partition; `Privacy`/`Annoyances`/`Regional` extensions are untouched by `FilterPipeline` and still use the Sprint 0 bundle-only path described above. `UpdatePlanner` reflects this: any manifest entry outside `.ads` surfaces as `.unsupportedGroup`, and a second `.ads` entry needing install in the same plan surfaces as `.groupConflict` rather than silently overwriting the first (only one compiled `.ads` output per install call is supported).
- **`ReloadCoordinator` timeout branch test coverage** — see the App Groups section above; accepted gap, tracked for a future sprint.
- **No real manifest-hosting endpoint** — Sprint 2's `ManifestClient`/`FilterDownloadClient` are complete and tested, but only against a mocked `HTTPSession`; there is no actual CDN/server serving `manifest.json` yet.
- **No caller of `UpdateCoordinator.run()`** — nothing in the app invokes it yet (no "Check for Updates" button, no launch-time check, no `BGAppRefreshTask`). See the blocking risk noted in the App Groups section above: wiring the first caller requires gating `ContentBlockerBootstrap`'s unconditional reinstall, or a real update gets silently reverted on next launch.
- **StoreKit / premium purchase flow** — `UpdatePlanner`'s `.skipPremium` case exists, but there's no purchase flow behind it; a never-installed premium filter is permanently skipped.
- **Background scheduling** — `UpdateCoordinator.run()` is written to be callable from either a foreground trigger or a future `BGAppRefreshTask` without modification, but nothing schedules it.
- **Uninstall on `.remove`** — `UpdatePlanner` correctly computes `.remove` for a filter dropped from the manifest, but `UpdateCoordinator.run()` only acts on `.install` actions (`compactMap` drops the rest) — a removed filter's rules and `installed_filters.json` entry are never actually deleted this sprint.
- **Downloaded temp-file cleanup** — `FilterDownloadClient`'s temp files (`DownloadedFilter.tempFileURL`) are never removed on any path (success, checksum failure, or rollback); harmless today since nothing calls `run()` repeatedly yet, but becomes a real leak once a scheduler does.
